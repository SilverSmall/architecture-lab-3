# Практична робота №3 — Refactoring under change

Ви отримали невеликий checkout backend. Він **працює** і проходить базові функціональні тести, але його архітектура навмисно містить проблеми. Ваше завдання — провести review, обґрунтовано переробити систему та перевірити дизайн новою вимогою.

> Використання AI дозволене. Оцінюється не походження коду, а розуміння рішень: здатність показати evidence, порівняти альтернативи, пояснити trade-offs і змінити власне рішення під час захисту.

## Швидкий старт

Потрібен Node.js 22.18+ (рекомендовано 24). Залежностей немає.

```bash
npm test
npm start
```

На старті всі функціональні тести мають проходити. Не змінюйте зовнішній формат `CheckoutController.checkout()` та очікування наявних тестів.

## Сценарій

Система оформлює замовлення, списує залишок і проводить оплату через Stripe. У коді є модулі Checkout, Orders, Payments, Inventory, Notifications і Reports. Архітектурні дефекти навмисні; README не перелічує їх, бо їх пошук є частиною оцінювання.

Робота виконується у такому порядку:

1. Запустіть тести та дослідіть codebase.
2. Проведіть review у `REVIEW.md`.
3. Для кожної суттєвої зміни ведіть `DECISIONS.md`.
4. **До кодування** зафіксуйте change impact prediction.
5. Виконайте свій рівень і зафіксуйте actual impact.
6. Переконайтеся, що базові тести не зламані.

## Change request

Додайте другого платіжного провайдера та статус `processing`. Публічне checkout API та наявна поведінка системи не повинні змінитися. Який саме провайдер потрібен, визначено у вимогах рівня 90; на рівнях 60/75 достатньо підготувати нормалізацію нового статусу без другого адаптера.

## Рівень 60 балів

- Знайдіть щонайменше 4 порушення архітектурних принципів. Для кожного вкажіть файл і рядок, принцип, практичний ризик та виправлення.
- Усуньте дублювання перетворення payment status.
- Локалізуйте provider-specific status mapping у Payments.
- Додайте підтримку статусу `processing`.
- Напишіть unit-тести для `paid`, `pending`, `failed`, `processing` та невідомого статусу.
- Збережіть проходження функціональних тестів.
- Опишіть щонайменше 2 рішення у `DECISIONS.md`.

## Рівень 75 балів

Усе з рівня 60, а також:

- Створіть єдиний public contract Payments: `authorizePayment(input): Promise<PaymentResult>`.
- Інші модулі не можуть імпортувати `payments/internal/*`.
- Перенесіть контроль залишків у публічний API Inventory: `inventory.reserve({ orderId, productId, quantity })`.
- Inventory має сам захищати invariant `available stock >= requested quantity`.
- Усуньте циклічні залежності між Orders і Payments.
- Перепишіть `calculateTotal()` як pure function з explicit inputs, без mutation аргументів та прихованих side effects.
- Додайте тести недостатнього залишку, невідомого payment status, purity розрахунку та незмінності checkout API.
- Опишіть щонайменше 4 рішення у `DECISIONS.md`.

## Рівень 90 балів

Усе з рівнів 60 і 75, а також:

- Введіть `PaymentGateway` і додайте `LiqPayGateway` як другий adapter.
- Під час додавання LiqPay **не змінюйте** Orders, Reports та Notifications.
- Додайте executable architecture fitness checks:
  - немає імпортів з `another-module/internal`;
  - немає циклічних залежностей;
  - немає прямого запису в storage іншого модуля.
- Команда `npm run check:architecture` повинна завершуватися з non-zero code при порушенні правила.
- Запускайте `npm test` і `npm run check:architecture` у GitHub Actions.
- Завершіть `ADR-001-payments-boundary.md`: переваги, недоліки та критерії винесення Payments у microservice.
- Проведіть review роботи колеги: 5–8 змістовних коментарів, щонайменше 2 про design; автор фіксує одну аргументовану зміну після review.
- Опишіть щонайменше 5 рішень у `DECISIONS.md`.

## Правила та обмеження

- Не можна видаляти або послаблювати наявні functional tests.
- Не можна змінювати очікуваний public response checkout.
- `shared/` не повинен стати місцем для business knowledge конкретного провайдера.
- Нові тести мають перевіряти поведінку, а не приватну реалізацію.
- Architecture check не може бути набором hardcoded PASS-повідомлень: він має аналізувати файли й падати на контрольному порушенні.
- Усі твердження у review повинні містити посилання на конкретне місце коду.

## Захист (7–10 хвилин)

Викладач обирає питання безпосередньо з вашого коду:

- покажіть evidence проблеми та поясніть її практичний наслідок;
- назвіть відхилену альтернативу й умови, за яких вона стала б кращою;
- поясніть, що зміниться при третьому provider або новому status;
- внесіть невелику зміну наживо;
- покажіть, як тест або fitness function ловить контрольне порушення;
- назвіть рішення, запропоноване AI, яке ви відхилили або виправили, і чому.

Оцінювання відповіді: `0` — немає розуміння; `1` — визначення терміна; `2` — зв'язок із власним кодом; `3` — причина, рішення та ефект; `4` — альтернативи, trade-off і прогноз наслідків.

## Definition of done

- `npm test` проходить;
- виконані всі вимоги обраного рівня;
- review, decisions та prediction спираються на реальні місця коду;
- студент може пояснити й модифікувати рішення без підготовленого тексту.
